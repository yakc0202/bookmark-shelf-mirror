A

전체 구조 — 무엇이 어디에 있나

이 구역만 읽어도 시스템의 뼈대를 안다.

서랍은 링크와 사진을 받아서, AI가 제목·요약·폴더를 붙인 카드로 정리하는 개인용 웹앱이다. 서버 컴퓨터를 켜 두지 않는다. 필요할 때만 잠깐 실행되는 AWS 서비스들이 일을 나눠서 한다.

  • 입구는 두 개다. 저장은 단축어가 Function URL로 바로 보낸다. 보기는 브라우저가 CloudFront를 거쳐 화면을 받는다.
  • 두뇌는 Lambda 두 개다. api 함수는 요청을 검사하고 데이터를 읽고 쓴다. worker 함수는 AI로 카드를 정리한다. → Lambda
  • 창고는 S3 버킷 하나다. 화면 파일, 데이터 파일 하나(data/cards.json), 사진 폴더(photos/)가 모두 여기에 있다. → S3
  • AI는 Codex를 먼저 쓴다. Codex가 한도에 걸리면 Claude로 바꾼다. 로그인 정보는 SSM Parameter Store에 있다.
  • 잊힌 일은 1시간마다 줍는다. EventBridge가 worker를 깨운다.
요청이 지나가는 길같은 S3 버킷 안B 구역 애니메이션에서 지금 쓰는 길
한 문장 요약. 단축어가 링크를 api에 보낸다 → api가 S3 데이터 파일에 카드를 추가하고 worker를 깨운다 → worker가 원본 글을 읽고 AI에 정리를 맡긴다 → 결과를 api를 통해 카드에 적는다 → 브라우저는 CloudFront로 화면을 받고 api로 카드 목록을 받는다.
B

움직임 따라가기 — 단계별 애니메이션

빨간 점이 요청 하나다. 단계마다 "누가, 무엇을, 무엇을 들고" 가는지 본다.

아이폰과 맥의 차이: 아이폰 공유 시트는 링크 하나를 넘긴다. 맥 Safari는 같은 페이지를 주소·제목 등 여러 항목으로 넘긴다. 단축어는 항목마다 링크를 찾아보고, 링크가 없는 항목은 건너뛴다. 그래서 맥에서도 카드가 하나만 생긴다. 공유 없이 단축어를 직접 실행하면 클립보드의 링크를 저장한다.

  • 3AI에게 정해진 모양(JSON 스키마)으로만 답하게 한다: 제목, 요약, 폴더, 태그, 충분한지 여부.
  • 4Codex를 먼저 쓴다. 읽기 전용 샌드박스라 파일을 바꾸지 못한다. 3분 안에 답이 없으면 실패로 본다.
  • 5"사용 한도 초과" 메시지면 1시간 동안 Codex를 쉬게 표시한다.
  • 6그다음 Claude Code를 쓴다. 도구·확장 기능을 모두 끈 안전 모드다.

cloud/site-gate.js · CloudFront Function. 브라우저 요청이 S3에 닿기 전에 실행된다(사진 경로는 제외).

const HOST = '__SITE_DOMAIN__';      // 배포 때 site.json 값으로 채움
const KEY_HASH = '__CLIENT_TOKEN_HASH__';

async function handler(event) {
  const req = event.request;
1  if (req.headers.host.value !== HOST)
    return { statusCode: 301, headers: { location: { value: 'https://' + HOST + req.uri } } };
2  if (PUBLIC.includes(req.uri) || req.uri.startsWith('/shortcuts/')) return req;
3  const cookie = req.cookies.shelf_key;
  if (cookie && sha256(decodeURIComponent(cookie.value)) === KEY_HASH) return req;
4  return { statusCode: 200, body: gatePage(!!cookie) };
}
  • 1정식 주소가 아니면(예: …cloudfront.net, 옛 도메인) 정식 주소로 넘긴다. 도메인 이관 때 이 성질로 옛 주소 → 새 주소 이동을 만든다.
  • 2아이콘과 단축어 파일은 키 없이 받게 둔다(아이폰이 설치할 때 쿠키가 없다).
  • 3쿠키에 든 키의 해시가 맞으면 S3로 보낸다.
  • 4아니면 S3까지 가지 않고 "접속 키 입력" 화면을 직접 돌려준다.

데이터와 상태 — 카드의 일생

data/cards.json 한 파일 안의 구조와, 카드 상태가 바뀌는 규칙.

E-1. 데이터 파일 구조

{
  "version": 1,
  "items":   [ 카드 551개 ],      // 북마크·사진·모음
  "memos":   [ 메모 ],
  "shares":  { 해시: {item_id, created} },  // 공유 링크
  "habits":  [ 습관 ],
  "ledger":  [ 가계부 ],  "ledger_plans": [ 예산 ],
  "schedule":{ todos, events, routines, passes, bookings, jobs }
}
카드 필드뜻
id링크는 주소 해시 앞 20자, 사진은 무작위 32자
url·title·summary원본 주소, AI가 지은 제목, 2~3문장 요약
folder·tags폴더 이름(예: 서울(카페)), 태그 목록
status오른쪽 그림의 상태
revision고칠 때마다 1씩 오르는 수정 번호(충돌 감지)
lease·lease_untilworker 임대표와 만료 시각(처리 중일 때만)
image_key·entries사진 파일 위치(photos/…jpg), 묶인 사진·이어진 글
deleted지운 표시(실제로 지우지 않아 되살릴 수 있음)

E-2. 상태 전이

  • queued 저장 직후. worker가 가져가기를 기다린다.
  • processing worker가 임대 중. 10분 안에 끝나지 않으면 다시 queued처럼 취급된다.
  • ready 정리 끝. 화면에 제목·요약이 보인다.
  • ai_waiting AI 한도·지연. 1시간 뒤 worker가 다시 가져간다(안전망 EventBridge).
  • needs_content 원본에서 읽을 글이 없다. 사용자가 본문을 보태면 다시 queued.
